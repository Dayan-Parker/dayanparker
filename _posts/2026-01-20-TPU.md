## Executive Summary

The WashU AI Racing team is building a Formula Student-sized autonomous electric car that uses a Convolutional Neural Network (CNN) to identify track boundary cones in real time. CNN inference acts as a bottleneck on the car's top speed, because delays in perception propagate through the entire autonomous pipeline. Our goal was to create a scalable hardware accelerator capable of competing with the car's current Nvidia Jetson Orin Nano, and to prototype it on an AMD Kria KV260 FPGA.

Our central design goal was to maximize parallel computation and minimize memory reads and CPU interrupts. We implemented a systolic array to allow input and weight data to flow through the hardware without redundant memory reads, and built a compiler that translates PyTorch CNNs into custom machine code — enabling the FPGA to run full matrix multiplications independently of the CPU.

<!--more-->

During the capstone we successfully implemented the custom CNN and compiler, achieving an mAP50 of 0.36 on the FOSCO cone detection dataset. A working 32×32 systolic matrix multiplier was implemented and fully validated in simulation at 8×8, 16×16, and 32×32 scales. The compiled instructions successfully controlled the entire device operation. Full end-to-end camera integration on the Kria was not completed due to the complexity of the board's camera IP architecture, but the standalone hardware modules provide a robust, scalable foundation for future development.

## 1. Motivation

<figure style="text-align: center;">
  <img src="https://dayan-parker.github.io/dayanparker/images/gazebo_track.png" alt="Simulated Formula Student AI track with cones" style="width:100%; height:auto;">
  <figcaption style="margin-top:8px; font-style:italic; color:#555;">Fig 1. Simulated Formula Student AI car navigating a realistic cone configuration.</figcaption>
</figure>

CNNs require a large number of Multiply-Accumulate (MAC) operations per image. A simplified example — a single 256×256 image convolved with a 3×3 kernel — requires 589,824 MACs. Comparing the theoretical throughput of three hardware platforms illustrates why hardware specialization matters:

$$\text{T}_{\text{CPU}} \approx \frac{589{,}824 \text{ MACs}}{1.2 \text{ GHz}} = 0.49 \text{ ms}$$

$$\text{T}_{\text{GPU}} \approx \frac{589{,}824}{40 \text{ TOPS}} = 14.75 \text{ ns (theoretical)}$$

$$\text{T}_{\text{TPU}} \approx \frac{589{,}824}{1{,}024 \times 300 \text{ MHz}} = 1.92 \text{ }\mu\text{s}$$

Although the GPU wins on raw throughput, it achieves this through image batching and frequent off-chip memory reads — introducing nondeterministic, high-variance latency. A systolic TPU design bypasses this bottleneck by allowing data to flow through processing elements without additional memory reads, producing deterministic, low-latency inference. In autonomous racing, where a car at 60 mph covers 2.7 cm per millisecond, deterministic latency is critical for precise trajectory planning.

## 2. Methods

### 2.1 Convolutional Neural Network

The CNN used with the systolic multiplier had to remain within strict memory and hardware limits, which ruled out off-the-shelf models. YOLOv8, even at reduced resolution, is too large to fit in the Kria's UltraRAM and uses layers (SiLU, residual connections, upsampling) that are complex to implement in RTL. We designed a custom CNN modeled on YOLO's architecture but restricted to hardware-friendly operations: 3×3 convolutions, SiLU activations, and max pooling. SiLU was chosen over ReLU because its smooth shape retains more gradient information during quantization.

<figure style="text-align: center;">
  <img src="https://dayan-parker.github.io/dayanparker/images/CNN_next_layer.png" alt="CNN convolutional layer" style="width:90%; height:auto;">
  <figcaption style="margin-top:8px; font-style:italic; color:#555;">Fig 3. Individual CNN layer: each output pixel is the sum of element-wise multiplications over a spatial neighborhood — a series of MAC operations that are mutually independent and fully parallelizable.</figcaption>
</figure>

The network was trained on 1,200 images from the Formula Student Objects in Context (FOSCO) dataset with a 90-10 train/validation split at 512×512 resolution. After training in PyTorch, weights were post-training quantized from 32-bit float to INT8 — reducing model size by 4× and enabling use of the Kria's DSP48 slices for high-speed integer arithmetic.

### 2.2 Compiler

Writing RTL machine code for an entire CNN by hand is not tractable. We built a compiler that reads PyTorch `.pt` weight files and generates custom opcodes sized for the physical systolic array. This made testing easy and allowed trivial swapping of models and array sizes. The compiler performs four main functions:

1. **Weight quantization and calibration** — Scales 32-bit float weights to INT8 by dividing by the running max and clipping to [−128, 127].
2. **Batch normalization fusion** — Algebraically folds batch norm into the convolution weights at compile time, eliminating run-time normalization. The fused weights and biases are:

$$W_{\text{fused}} = W \cdot \frac{\gamma}{\sqrt{\sigma^2 + \epsilon}}, \quad B_{\text{fused}} = (b - \mu) \cdot \frac{\gamma}{\sqrt{\sigma^2 + \epsilon}} + \beta$$

3. **AXI-Stream packing** — Flattens multidimensional weight tensors into 32-bit words with correct byte alignment and endianness for the FPGA's AXI-Stream interface.
4. **Dynamic tiling with double buffering** — Because early layer feature maps exceed on-chip BRAM capacity, the compiler chunks the M dimension (image pixels) into 1,024-element tiles, assigning alternating base addresses (0 or 8192). This generates the exact instruction sequence needed to operate the hardware's ping-pong double buffer, hiding DMA transfer latency behind active computation.

### 2.3 Systolic Processor

The systolic processor (`Systolic_Controller_CP`) instantiates all components needed to store data, configure, and compute as shown in the block diagram below.

<figure style="text-align: center;">
  <img src="https://dayan-parker.github.io/dayanparker/images/tpu_block_diagram.png" alt="Systolic processor block diagram" style="width:100%; height:auto;">
  <figcaption style="margin-top:8px; font-style:italic; color:#555;">Fig 6. Complete systolic processor block diagram: input/output/weight memory, systolic matrix multiplier, vector processing unit, control FSM, and AXI buses.</figcaption>
</figure>

**Control FSM** — The brain of the controller. Fed by an instruction RAM with an iterating program counter, the FSM decodes opcodes and sequences the hardware pipeline through states: `IDLE_DECODE → DECODE → INIT_LAYER → CALC_TILE_ADDR → TRIGGER_ARRAY → WAIT_ARRAY → UPDATE_COUNTERS`. The FSM manages a dynamic tiling loop, configuring accumulator control signals based on the K-dimension to correctly fold deep-channel partial sums without overflow.

<figure style="text-align: center;">
  <img src="{{ '/images/systolic_controller_FSM.png' | absolute_url }}" alt="Systolic controller FSM" style="width:80%; height:auto;">
  <figcaption style="margin-top:8px; font-style:italic; color:#555;">Fig 7. Control FSM state diagram — decodes instructions from IRAM and sequences execution on the systolic array and VPU.</figcaption>
</figure>

**Systolic Array** — A 32×32 grid of Processing Elements (PEs). Each PE takes an 8-bit input and weight, performs a MAC, and passes both to adjacent PEs. Input activations flow horizontally; weights flow vertically. A single memory read of an activation value is reused across an entire row, and a single weight read is reused across an entire column — eliminating the von Neumann bottleneck.

<figure style="text-align: center;">
  <img src="{{ '/images/systolic_PE.png' | absolute_url }}" alt="Processing element diagram" style="width:60%; height:auto;">
  <figcaption style="margin-top:8px; font-style:italic; color:#555;">Fig 8. Systolic PE with 8-bit inputs, 16-bit intermediate product, and 32-bit accumulated output register.</figcaption>
</figure>

<figure style="text-align: center;">
  <img src="{{ '/images/TPU_diagram.png' | absolute_url }}" alt="Systolic PE array data flow" style="width:100%; height:auto;">
  <figcaption style="margin-top:8px; font-style:italic; color:#555;">Fig 9. Systolic PE array — activations flow left-to-right, weights flow top-to-bottom, each reused across the full row or column.</figcaption>
</figure>

**Vector Processing Unit (VPU)** — Post-processes the 32-bit partial sums from the systolic array: applies the activation function (SiLU via precomputed 256-entry lookup table), re-quantizes outputs to INT8, and adds fused bias values. The lookup table approach allows highly nonlinear functions at zero additional computational cost.

**RAMs** — All weights are stored in UltraRAM (≈1 MB, `xpm_memory_tdpram`). Input activations use a 256 KB dual-port BRAM with asymmetric port widths: the write side is 32-bit wide (matching AXI-Stream DMA), while the read side is 64-bit wide so the controller can fetch 8 pixels per cycle to feed the full left flank of the array. This inherently supports the ping-pong tiling scheme.

**Data Buses** — All communication uses AXI4-Lite (configuration registers) and AXI-Stream (data in/out via DMA). Limiting discrete I/O to clock, reset, and a single interrupt allows the systolic controller internals to be modified without touching connected modules.

### 2.4 Hardware Design

Camera data is streamed from an Arducam 5MP OV5647 through the Kria's MIPI-CSI connector into on-board DDR4 RAM, then transferred to the systolic controller via DMA.

<figure style="text-align: center;">
  <img src="{{ '/images/SimpleBD.png' | absolute_url }}" alt="Camera to systolic pipeline block diagram" style="width:100%; height:auto;">
  <figcaption style="margin-top:8px; font-style:italic; color:#555;">Fig 10. Minimal block diagram: Camera → Zynq Processor (DDR4) → DMA_0 → Systolic Controller → DMA_1 → output.</figcaption>

The Kria was programmed using a device tree generated from the exported hardware `.xsa` file, combined with a bitstream file loaded via `xmutil`. This approach bypassed Vitis debug configuration issues and gave direct control over the device tree.

### 2.5 Feasibility Study

Our maximum theoretical throughput on the Kria KV260 with a 32×32 systolic array at 350 MHz:

$$\text{TOPS} = 1{,}024 \text{ MACs} \times 2 \times 350 \text{ MHz} \approx 0.72 \text{ TOPS}$$

For a 64×64×16 feature map typical of an early CNN layer:

$$\text{Latency} = \frac{W \times H \times C}{\text{MatSize}} \times T_{\text{clk}} \approx 54.61 \text{ }\mu\text{s}$$

This is orders of magnitude faster than the millisecond-scale latency of GPU kernel launches and memory transfers, and unlike the Jetson's batched throughput metric, it is deterministic per-frame.

## 3. Results

Each module — systolic processing elements, data setup, VPU, and accumulator — was tested individually in Vivado behavioral simulation and cross-validated against Python/PyTorch-generated reference data. Once modules were combined into the top-level controller, full 8×8, 16×16, and 32×32 matrix multiplications were performed and verified in simulation.

The custom CNN achieved an mAP50 of **0.36** and precision of **0.85** on the FOSCO validation set. The relatively low recall (0.26) reflects the dataset's difficulty: it contains images from Formula Student events with many small, distant, blurred cones at 512×512 resolution, combined with the accuracy cost of INT8 quantization. The compiler's bounding box outputs confirmed that the end-to-end pipeline functions correctly — the accuracy bottleneck is in the model's size constraints, not a hardware flaw.

A full bitstream of the block diagram was synthesized and programmed onto the Kria. The board successfully booted Ubuntu on the ZYNQ processor while simultaneously running Vivado ILAs for hardware debugging.

## 4. Discussion

**Tiling complexity** — The most significant engineering hurdle was scaling from single matrix multiplications to full-layer computation. Early CNN feature maps are far larger than the 32×32 physical array, requiring dynamic tiling with partial-sum accumulation. Implementing this entirely in the FSM caused quadratic instruction growth with the ratio of layer size to array size. Moving tiling logic into a smarter software-visible controller (rather than hard-wired RTL) would be the right architectural pivot for the next iteration.

**Kria abstraction** — The AMD Kria KV260 offers excellent price-to-performance and 6× more DSP slices than the PYNQ board used in prior work. However, its ecosystem is heavily optimized for Vitis-based deployment of pre-built AI models, not for custom RTL developers. Conflicts between Vivado and the ZYNQ processing system during debugging, and the complexity of the camera IP pipeline, consumed significant time. A more conventionally documented FPGA, or an established MIPI-CSI IP core, would remove these abstraction barriers.

**Scalability** — The compiler architecture cleanly decouples model design from hardware constraints. Any PyTorch model can be substituted into the pipeline without hardware changes. Increasing the systolic array size and UltraRAM allocation is straightforward. If implemented in an ASIC medium at comparable clock speeds, the design's latency would be competitive with the Jetson's GPU.

---

## 5. Conclusion

This project proved that a TPU-inspired systolic architecture can provide deterministic, low-latency CNN inference as a viable alternative to general-purpose GPUs for autonomous racing. The 32×32 systolic array and VPU were fully validated in simulation. The compiler pipeline — quantization, batch norm fusion, AXI packing, and dynamic tiling — successfully bridged PyTorch model training to raw RTL execution. While end-to-end camera integration on the Kria was not completed within the semester, the standalone modules establish a clear, scalable roadmap. The trajectory for WUAIR's computer vision stack has been permanently altered toward deterministic, hardware-accelerated perception.
